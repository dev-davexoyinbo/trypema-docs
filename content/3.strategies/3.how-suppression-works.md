This page is a standalone deep-dive into how Trypema's suppressed strategy works. It is aimed at readers who understand rate limiting generally and want to understand *precisely* what the suppression algorithm does and why.

For usage examples and API surface, see [Suppressed Strategy](/strategies/suppressed).

## Motivation

Traditional rate limiters use a hard cutoff: below the limit everything passes, above it everything is rejected. This creates a cliff-edge effect. At the exact threshold, a small increase in traffic causes all requests to fail simultaneously, which can trigger thundering-herd retries and cascading failures.

Trypema's suppressed strategy takes a different approach: **probabilistic suppression**. As traffic approaches and exceeds the target rate, the limiter begins denying an increasing *fraction* of requests rather than all of them at once. This produces smooth degradation:

- Clients that are slightly over the limit still get most of their requests through.
- As traffic grows further, progressively more requests are denied.
- At a configurable hard limit, all requests are denied (full suppression).

The result is that some throughput is preserved for all clients rather than fully blocking at a threshold. Systems using the suppressed strategy can degrade gracefully by shedding load proportionally rather than collapsing under a sudden cliff-edge rejection.

This approach is inspired by [Ably's distributed rate limiting at scale](https://ably.com/blog/distributed-rate-limiting-scale-your-platform).

## The three operating regimes

For a given key with `rate_limit` (requests per second) and `window_size_seconds`, the suppressed strategy defines two thresholds:

- **Soft limit** (window capacity): `window_size_seconds * rate_limit`
- **Hard limit**: `window_size_seconds * rate_limit * hard_limit_factor`

The strategy operates in three regimes based on where the key's current usage falls relative to these thresholds.

### 1. Below capacity

**Condition:** `accepted_usage < window_size_seconds * rate_limit` (the soft limit)

**Returns:** `RateLimitDecision::Allowed`

**Behaviour:** All requests are admitted. No suppression logic is involved. This is the normal operating mode for keys that are within their budget.

### 2. At or near capacity (soft to hard limit range)

**Condition:** accepted usage is at or above the soft limit but observed usage has not reached the hard limit.

**Returns:** `RateLimitDecision::Suppressed { is_allowed, suppression_factor }`

**Behaviour:** A suppression factor between `0.0` and `1.0` is computed (and cached). Each request is probabilistically admitted with probability `1.0 - suppression_factor`. The higher the factor, the more requests are denied. Both admitted and denied requests are recorded in the counters.

### 3. Over the hard limit

**Condition:** `observed_usage >= window_size_seconds * rate_limit * hard_limit_factor`

**Returns:** `RateLimitDecision::Suppressed { is_allowed: false, suppression_factor: 1.0 }`

**Behaviour:** Full suppression. All requests are denied until usage falls back under the hard limit. This acts as an absolute ceiling to prevent runaway acceptance.

::warning
The suppressed strategy never returns `Rejected`. Over the hard limit it returns `Suppressed { is_allowed: false, suppression_factor: 1.0 }`. Always gate your request on `is_allowed`.
::

## The suppression factor formula

The suppression factor determines what fraction of requests should be denied. It is computed from the key's current traffic pattern:

```text
average_rate_in_window = total_observed / window_size_seconds
rate_in_last_1000ms    = sum of bucket counts in the last 1000ms
perceived_rate         = max(average_rate_in_window, rate_in_last_1000ms)
suppression_factor     = 1.0 - (rate_limit / perceived_rate)
```

### Why `perceived_rate` takes the max of both terms

The formula uses two rate estimates and takes the higher one:

- **`average_rate_in_window`**: the average rate across the entire sliding window. This gives a stable, smoothed view of the key's traffic. It prevents suppression from collapsing to zero too quickly after a spike (the spike's counts remain in the window average for `window_size_seconds`).

- **`rate_in_last_1000ms`**: the rate observed in the most recent 1 second. This makes suppression react fast to short spikes. If a burst arrives, the 1-second term will spike before the window average catches up, causing suppression to engage immediately.

By taking the max, the algorithm is both responsive to sudden spikes (via the 1-second term) and stable during sustained overload (via the window average).

### Clamping

- If `perceived_rate <= rate_limit`, the factor is `<= 0.0` and suppression is bypassed entirely (the key is below capacity).
- The factor is clamped to at most `1.0` (full suppression).

## What happens at each factor value

The suppression factor directly controls the probability of admission:

| `suppression_factor` | Probability of admission | Effect |
| --- | --- | --- |
| `0.0` | 100% | All requests pass through (below capacity) |
| `0.3` | 70% | ~70% of requests admitted, ~30% denied |
| `0.5` | 50% | ~50% admitted, ~50% denied |
| `0.7` | 30% | ~30% admitted, ~70% denied |
| `1.0` | 0% | All requests denied (full suppression) |

### Worked example

Suppose `rate_limit = 10 req/s` and `perceived_rate = 14 req/s`:

```text
suppression_factor = 1.0 - (10.0 / 14.0) = 1.0 - 0.714 = 0.286
```

About 71% of requests will be admitted, and about 29% will be denied. The admitted rate will be approximately `14 * 0.714 = 10 req/s`, which is close to the target rate.

## The `hard_limit_factor` parameter

`hard_limit_factor` controls the gap between the "soft limit" (where suppression begins) and the "hard limit" (where full suppression kicks in).

```text
soft_limit = rate_limit                        (suppression begins here)
hard_limit = rate_limit * hard_limit_factor    (full suppression here)
```

The hard limit factor must be >= 1.0 (`HardLimitFactor::try_from(value)` fails if `value < 1.0`). Default is `1.0`.

### How different values behave

- **`hard_limit_factor = 1.0`** (default): The soft limit and hard limit are the same point. Suppression starts and reaches `1.0` at the same threshold. This produces hard cutoff behaviour similar to the absolute strategy. There is no gradual ramp.

- **`hard_limit_factor = 1.5`**: The hard limit is 50% above the soft limit. There is a headroom range where suppression gradually ramps from `0.0` to `1.0`. Example: with `rate_limit = 10 req/s`, suppression begins at `10 req/s` and reaches full suppression at `15 req/s`.

- **`hard_limit_factor = 2.0`**: The hard limit is 100% above the soft limit. Even more gradual ramp. With `rate_limit = 10 req/s`, the range is `10` to `20 req/s`.

::note
For most use cases, `hard_limit_factor = 1.5` is a good starting point. It provides 50% burst headroom with smooth degradation.
::

## Counter tracking

The suppressed strategy maintains two counters per key in its sliding window:

- **`total`** (observed): the total number of calls seen for the key, regardless of whether they were admitted or denied.
- **`declined`**: the number of calls denied by suppression (`is_allowed: false`).

Both counters are **always** incremented:

1. Every call increments `total` by `count`.
2. If the call is denied (`is_allowed: false`), `declined` is also incremented by `count`.
3. If the call is admitted, only `total` is incremented.

You can derive accepted usage as:

```text
accepted = total - declined
```

This design means the limiter always has full visibility into both the offered load (total) and the actual throughput (accepted). The `total` counter drives the suppression factor calculation, while `accepted` is used to determine which regime the key is in.

## Suppression factor caching

Computing the suppression factor requires iterating over recent buckets (to calculate `rate_in_last_1000ms`) and reading window totals. Under high throughput, doing this on every call would be expensive.

To amortise this cost, the computed factor is **cached per key** for `suppression_factor_cache_ms`:

- **Local provider:** cached in-memory using `Instant` timestamps. The factor is recomputed only when the cache has expired.
- **Redis provider:** cached in Redis as a string with a `SET ... PX` TTL. Multiple calls within the TTL reuse the cached value.

### Trade-offs

| Cache duration | Reaction speed | CPU/Redis cost |
| --- | --- | --- |
| Short (10-50ms) | Fast reaction to traffic changes | More frequent recomputation |
| Long (100-1000ms) | Slower reaction to sudden spikes | Less overhead |

The default is `100ms`, which is a good starting point for most workloads.

## Differences between Local, Redis, and Hybrid

All three providers use the same suppression algorithm. The core logic (three regimes, suppression factor formula, probabilistic admission) is identical. The differences are in where state is stored and how caching works:

### Local provider

- State is stored in-process using `DashMap` and atomic counters.
- Suppression factor is cached in-memory with `Instant` timestamps.
- Bucket expiry uses `Instant::elapsed().as_millis()` (millisecond granularity, lazy eviction).
- Decisions are synchronous (no I/O).
- State is per-process and not shared across instances.

### Redis provider

- State is stored in Redis using Lua scripts (atomic per-call).
- Suppression factor is cached in Redis with `SET ... PX` TTL.
- Bucket expiry uses Redis server time in milliseconds inside Lua scripts.
- Each `inc()` and `get_suppression_factor()` call is one Redis round-trip.
- State is shared across all processes using the same Redis instance.

### Hybrid provider

- Maintains local in-memory state per key with a background actor that periodically flushes to Redis.
- The suppression factor comes from the last Redis read and is used for probabilistic admission on the local fast-path.
- Between flushes, admission decisions are served from local state with no Redis I/O.
- State can lag behind the true Redis state by up to `sync_interval_ms`.
- The `Suppressing` state uses *probabilistic* suppression based on the cached factor (not necessarily full suppression).

## Concrete worked example

Consider this configuration:

- `rate_limit = 10 req/s`
- `window_size_seconds = 60`
- `hard_limit_factor = 1.5`

This gives us:

- **Soft limit (window capacity):** `60 * 10 = 600` requests in the window
- **Hard limit:** `60 * 10 * 1.5 = 900` requests in the window

### Scenario: traffic ramps from 0 to 900+

**Phase 1: 0 to 600 requests in the window**

All requests return `Allowed`. No suppression is active. The suppression factor is `0.0`.

**Phase 2: 600 to ~700 requests (accepted ~600, observed ~700)**

Suppression begins. Suppose the window now has 700 total observed requests, with an even distribution:

```text
average_rate_in_window = 700 / 60 = 11.67 req/s
rate_in_last_1000ms    = 12 req/s  (example)
perceived_rate         = max(11.67, 12) = 12.0
suppression_factor     = 1.0 - (10.0 / 12.0) = 0.167
```

About 83% of requests are admitted. The strategy returns `Suppressed { suppression_factor: 0.167, is_allowed: true/false }`.

**Phase 3: ~800 requests observed**

```text
average_rate_in_window = 800 / 60 = 13.33 req/s
rate_in_last_1000ms    = 15 req/s  (traffic is spiking)
perceived_rate         = max(13.33, 15) = 15.0
suppression_factor     = 1.0 - (10.0 / 15.0) = 0.333
```

About 67% of requests are admitted. Suppression is noticeably active.

**Phase 4: 900+ requests observed (hard limit)**

Once observed usage reaches 900 (the hard limit), the strategy bypasses the factor calculation and forces `suppression_factor = 1.0`:

```text
suppression_factor = 1.0
```

All requests are denied: `Suppressed { is_allowed: false, suppression_factor: 1.0 }`.

This continues until enough time passes for old buckets to expire and usage drops below the hard limit.

## The `get_suppression_factor()` API

All three providers expose a method to fetch the current suppression factor for a key without recording any increment:

```rust
// Local (sync)
let factor = rl.local().suppressed().get_suppression_factor("user_123");

// Redis (async)
// let factor = rl.redis().suppressed().get_suppression_factor(&key).await.unwrap();

// Hybrid (async)
// let factor = rl.hybrid().suppressed().get_suppression_factor(&key).await.unwrap();
```

Returns a value in `[0.0, 1.0]`:

- `0.0` -- no suppression (below capacity or key not found)
- `0.0 < sf < 1.0` -- partial suppression (at capacity)
- `1.0` -- full suppression (over hard limit)

This is useful for:

- **Observability:** export the factor as a metric to monitor how close keys are to their limits.
- **Dashboards:** show per-key suppression levels in real-time.
- **Debugging:** understand why calls are being suppressed for a specific key.

The method returns the cached value if it was computed within `suppression_factor_cache_ms`. Otherwise, it recomputes the factor from the current sliding window state.
