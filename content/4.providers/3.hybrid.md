The hybrid provider is a high-throughput alternative to the Redis provider.

It is Redis-backed, but makes most admission decisions locally using an in-memory fast-path, then
periodically flushes local increments to Redis.

Access it through `RateLimiter::hybrid()`.

## When to use

Use hybrid when you want:

- lower steady-state latency (no per-request Redis round trip on the fast path)
- reduced Redis load (batched commits)
- a bounded amount of approximation: Redis state can lag by up to `sync_interval_ms`

If you need decisions to always reflect the latest Redis state, use the Redis provider.

## Requirements

- Redis >= 6.2
- One async runtime feature enabled: `redis-tokio` or `redis-smol`

## Create a hybrid-backed limiter (Tokio)

```rust
use std::sync::Arc;

use trypema::{HardLimitFactor, RateGroupSizeMs, RateLimit, RateLimiter, RateLimiterOptions, SuppressionFactorCacheMs, WindowSizeSeconds};
use trypema::hybrid::SyncIntervalMs;
use trypema::local::LocalRateLimiterOptions;
use trypema::redis::{RedisKey, RedisRateLimiterOptions};

// Create Redis connection manager
let client = redis::Client::open("redis://127.0.0.1:6379/").unwrap();
let connection_manager = client.get_connection_manager().await.unwrap();

let sync_interval_ms = SyncIntervalMs::default();

let rl = Arc::new(RateLimiter::new(RateLimiterOptions {
    local: LocalRateLimiterOptions {
        window_size_seconds: WindowSizeSeconds::try_from(60).unwrap(),
        rate_group_size_ms: RateGroupSizeMs::try_from(10).unwrap(),
        hard_limit_factor: HardLimitFactor::try_from(1.5).unwrap(),
        suppression_factor_cache_ms: SuppressionFactorCacheMs::default(),
    },
    redis: RedisRateLimiterOptions {
        connection_manager,
        prefix: None,
        window_size_seconds: WindowSizeSeconds::try_from(60).unwrap(),
        rate_group_size_ms: RateGroupSizeMs::try_from(10).unwrap(),
        hard_limit_factor: HardLimitFactor::try_from(1.5).unwrap(),
        suppression_factor_cache_ms: SuppressionFactorCacheMs::default(),
        sync_interval_ms,
    },
}));

rl.run_cleanup_loop();

let key = RedisKey::try_from("user_123".to_string()).unwrap();
let rate = RateLimit::try_from(10.0).unwrap();

let _ = rl.hybrid().absolute().inc(&key, &rate, 1).await.unwrap();
let _ = rl.hybrid().suppressed().inc(&key, &rate, 1).await.unwrap();
```

## State machine

Each key transitions through states internally:

### Absolute strategy

- `Undefined` -- first call reads Redis to initialise local state.
- `Accepting` -- serving from local counter (no Redis I/O per request).
- `Rejecting` -- rejection cache based on oldest bucket's TTL.

### Suppressed strategy

- `Undefined` -- first call reads Redis to initialise.
- `Accepting` -- below capacity; all requests allowed from local state.
- `Suppressing` -- at/above capacity; *probabilistic* admission based on the suppression factor from the last Redis read. The factor determines the fraction of requests denied (partial or full suppression depending on the factor value). This is the same probabilistic algorithm as the local and Redis suppressed strategies.

::note
The `Suppressing` state does not mean "all requests denied". It means the suppression factor is applied probabilistically: requests are admitted with probability `1.0 - suppression_factor`. Only when the factor reaches `1.0` (over the hard limit) are all requests denied.
::

### Thundering herd prevention

Each key has its own `tokio::sync::Mutex`. When local state is exhausted and a Redis read is needed, only one task performs the read; others wait and then re-check the refreshed state.

## Notes

- Hybrid uses `RedisKey` with the same validation rules as the Redis provider.
- `sync_interval_ms` is configured in `RedisRateLimiterOptions` and controls flush cadence. The pure Redis provider ignores this value.
- A good rule of thumb is `sync_interval_ms <= rate_group_size_ms`.
