**Status:** Released · November 14, 2026

Version 3.0.0 replaces the `RateLimiterBuilder` trait and the three provider builder types with
one builder struct. The same builder builds a provider or one of its two limiters. This release
breaks code that names the builder types; see
[Migrating from 2.x to 3.0](#migrating-from-2x-to-30).

## Breaking changes

- `RateLimiterBuilder` is now a struct, `RateLimiterBuilder<B, T = AnyTarget>`, not a trait. `B`
  is the backend and `T` is the target of `build()`.
- Removed `LocalRateLimiterBuilder`, `RedisRateLimiterBuilder`, and `HybridRateLimiterBuilder`.
- The builder settings are now methods of the struct. A backend setting is only on the builders
  of its backend: `prefix` on Redis and hybrid, and `sync_interval`, `allowed_lag`, and
  `allowed_lag_applies_to_rejections` on hybrid.
- Generic code with a bound on the old trait uses the sealed `RateLimiterTarget` trait.

## Added

- Added the backend constructors `RateLimiterBuilder::local()`,
  `RateLimiterBuilder::redis(connection_manager)`, and
  `RateLimiterBuilder::hybrid(connection_manager)`. The Redis and hybrid constructors need the
  `redis-tokio` or `redis-smol` feature.
- `build()` returns `Arc<T>`. The type that the caller expects selects the target: the provider
  of the backend or one of its two limiters. A turbofish also selects it, for example
  `build::<LocalRateLimiterProvider>()`. A target of another backend does not compile.
- Added a `builder()` shortcut to each of the six limiters, for example
  `AbsoluteLocalRateLimiter::builder()` and
  `SuppressedHybridRateLimiter::builder(connection_manager)`. Like the provider shortcuts, a
  limiter shortcut fixes the target, so its `build()` needs no annotation.
- Added `start_cleanup_loop()` and `stop_cleanup_loop()` to each limiter. Both are idempotent.
- Added the backend types `local::LocalBackend`, `redis::RedisBackend`, and
  `hybrid::HybridBackend`, the default target `AnyTarget`, and the sealed trait
  `RateLimiterTarget`.

```rust
use std::sync::Arc;
use trypema::RateLimiterBuilder;
use trypema::hybrid::AbsoluteHybridRateLimiter;
use trypema::redis::RedisKey;

let limiter: Arc<AbsoluteHybridRateLimiter> = RateLimiterBuilder::hybrid(connection)
    .prefix(RedisKey::try_from("ip-ban")?)
    .allowed_lag_applies_to_rejections(true)
    .build()?;
```

## Directly built limiters

- A directly built limiter does not create the state, Lua scripts, or background workers of the
  other strategy.
- A limiter built with a prefix uses the same Redis keys as the strategy of a provider with the
  same prefix. Thus the two share state.
- A directly built limiter runs its own stale-state cleanup loop. `build()` starts it unless
  cleanup is disabled. The loop ends within one cleanup interval after the last `Arc` of the
  limiter drops or after `stop_cleanup_loop()`. On a hybrid limiter, the synchronization worker
  also ends after the last `Arc` drops.
- The builder accepts every shared setting for every target. The absolute limiters do not use
  `hard_limit_factor` and `suppression_factor_cache_period`. The suppressed hybrid limiter does
  not use `allowed_lag_applies_to_rejections`.

## Fixed

- The epoch task of a hybrid limiter continued for up to 15 seconds after the limiter was dropped.
  Now it ends immediately.

## Migrating from 2.x to 3.0

Code that calls only the provider shortcuts compiles without change. A chain such as
`HybridRateLimiterProvider::builder(connection).window_size(window).build()?` returns the same
`Arc` as before. In this code, `use trypema::RateLimiterBuilder;` is now an unused import, because
the settings are methods of the struct. Remove it.

Code that names a removed builder type writes the builder type of the shortcut instead:

| 2.x | 3.0 |
| --- | --- |
| `LocalRateLimiterBuilder` | `RateLimiterBuilder<LocalBackend, LocalRateLimiterProvider>` |
| `RedisRateLimiterBuilder` | `RateLimiterBuilder<RedisBackend, RedisRateLimiterProvider>` |
| `HybridRateLimiterBuilder` | `RateLimiterBuilder<HybridBackend, HybridRateLimiterProvider>` |

A backend constructor such as `RateLimiterBuilder::local()` returns
`RateLimiterBuilder<LocalBackend>`. Its target comes from the caller.

```rust
use trypema::{
    BucketSize, RateLimiterBuilder,
    local::{LocalBackend, LocalRateLimiterProvider},
};

type LocalBuilder = RateLimiterBuilder<LocalBackend, LocalRateLimiterProvider>;

fn tune(builder: LocalBuilder) -> LocalBuilder {
    builder.bucket_size(BucketSize::milliseconds_or_panic(50))
}

let provider = tune(LocalRateLimiterProvider::builder()).build()?;
```

A bound on the old trait, such as
`fn build<B: RateLimiterBuilder>(builder: B) -> Arc<B::Provider>`, becomes a bound on
`RateLimiterTarget`:

```rust
use std::sync::Arc;
use trypema::{RateLimiterBuilder, RateLimiterTarget, TrypemaError, WindowSize};
use trypema::local::LocalRateLimiterProvider;

fn build_with_window<T: RateLimiterTarget>(
    builder: RateLimiterBuilder<T::Backend, T>,
) -> Result<Arc<T>, TrypemaError> {
    builder.window_size(WindowSize::seconds_or_panic(10)).build()
}

let provider = build_with_window(LocalRateLimiterProvider::builder())?;
```
