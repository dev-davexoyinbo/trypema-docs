## Redis backend performance (comparison)

This suite compares the backend cost of three Redis rate limiting approaches under the same client concurrency and runtime.

How to run:

```bash
make stress-redis-compare
```

Environment:

- Redis: Docker Compose (`compose.yaml`) on Docker Desktop (server `linux/arm64`)
- Client: 16 threads
- Duration: 30s per case

Backends compared:

- `trypema` Redis provider (Lua sliding-window)
- `redis-cell` module (`CL.THROTTLE`)
- GCRA Lua script (equivalent to `go-redis/redis_rate` allowN)

Caveat: semantics differ (sliding window vs GCRA), so results are backend-cost comparisons, not strict behavioral equivalence.

Command captured (for reference):

```bash
make stress-redis-compare
```

Module-based approaches (like `redis-cell`) tend to be faster because the logic runs as native Redis module code with less Lua interpreter overhead and fewer internal steps than multi-op Lua scripts.

## Results (Stress / Load harness)

These results are copied from a `make stress` run (the `trypema-stress` harness). Units:

- Throughput: `ops_per_s` (ops/sec)
- Latency: `lat_us` in microseconds (sampled every `sample_every=100` ops)

`key_dist` controls how the stress test chooses rate-limiter keys (users) on each operation:

- `hot`: always uses a single key (`user_0`). `key_space` is ignored (effectively 1 key).
- `uniform`: picks a random key uniformly from `key_space` keys (`user_0..user_{key_space-1}`).
- `skewed`: with probability `hot_fraction` uses `user_0`, otherwise picks uniformly from the remaining keys (`user_1..`). (`key_space` controls how many exist.)

## How to re-run

```bash
# From the trypema repo root
make bench-local
make bench-redis
```

## Caveats

- Local benches are disabled when Redis features are enabled; run local benches without `--features redis-tokio`.
- Redis numbers include Docker/virtualization and local networking overhead.
- Compare deltas on the same machine/config whenever possible.
